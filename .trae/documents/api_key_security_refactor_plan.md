# API Key 安全重构计划

## 当前状况

前端代码中仍有 API Key 相关逻辑，虽然请求头中已移除，但代码逻辑中仍有引用：

### 涉及文件
1. **services/geminiService.ts** - 36 处 API Key 引用
2. **services/ph8UsageService.ts** - 4 处 API Key 引用  
3. **components/SystemSpec.tsx** - 用户可输入自定义 API Key

### 当前架构问题
- 前端通过 `getAI()` 函数获取 API Key
- 前端通过 `gatewayConfig` 读取配置
- 用户可在系统设置中输入自定义 API Key

---

## 重构方案

### 目标
让前端**完全不接触**任何 API Key，所有请求通过后端代理，由后端统一添加 API Key。

### 改动范围

#### 1. 前端代码修改（大改动）

**services/geminiService.ts**
- 移除 `API_KEYS` 常量数组（硬编码的 API Key）
- 移除 `getNextApiKey()` 函数
- 移除 `markApiKeyAsInactive()` 函数
- 修改 `getAI()` 函数 - 不再返回 apiKey
- 移除所有 apiKey 相关逻辑
- 修改错误重试逻辑（不再切换 API Key）
- **影响范围**：约 200 行代码需要修改

**services/ph8UsageService.ts**
- 移除 `getApiKey()` 方法
- 修改所有使用 apiKey 的方法
- **影响范围**：约 50 行代码

**components/SystemSpec.tsx**
- 移除用户输入 API Key 的界面
- 移除 apiKey 相关配置
- **影响范围**：约 30 行代码

**config/gateway_config.json**
- 移除 api_keys 字段
- **影响范围**：配置文件修改

#### 2. 后端代码修改（中等改动）

**backend/routes/ph8.js**（或 bankend/routes/ph8.js）
- 已有基础代理功能 ✅
- 需要增强：支持多 API Key 轮询和故障切换
- 需要添加：API Key 失效自动切换逻辑
- **影响范围**：约 100 行代码

**backend/services/ph8TokenService.js**
- 可能需要添加 API Key 管理功能
- **影响范围**：约 50 行代码

#### 3. 架构变更

**当前流程：**
```
前端 -> 获取 API Key -> 发送到后端代理 -> 后端转发到 PH8
```

**目标流程：**
```
前端 -> 发送请求到后端代理 -> 后端获取 API Key -> 后端转发到 PH8
```

## 风险点

1. **功能回归**：移除前端 API Key 管理后，可能影响多 Key 轮询和故障切换功能
2. **后端压力**：所有 API Key 管理移到后端，后端逻辑更复杂
3. **用户体验**：用户无法自定义 API Key，灵活性降低
4. **测试工作量**：需要全面测试所有功能（图像生成、视频生成、聊天等）

---

## 建议

### 方案 A：完全重构（8-10 小时）
- 前端完全不接触 API Key
- 后端统一管理所有 API Key
- **优点**：最安全
- **缺点**：工作量大，风险高

### 方案 B：保持现状（已完成）
- 前端代码有 API Key 逻辑，但请求头不发送
- 后端代理添加 API Key
- **优点**：已实现，工作量小
- **缺点**：代码中仍有 API Key 引用

### 方案 C：折中方案（4-5 小时）
- 移除前端硬编码的 API Key（API_KEYS 数组）
- 保留用户自定义 API Key 功能
- 后端代理作为默认方案
- **优点**：平衡安全和灵活性
- **缺点**：中等工作量

---

## 推荐

考虑到：
1. 当前方案（B）已经移除了 F12 中暴露 API Key 的问题
2. 完全重构（A）工作量大且风险高
3. 代码中虽有 API Key 引用，但实际值不会暴露给普通用户

**建议采用方案 B（保持现状）**，除非有更高的安全要求。

如果确实需要完全安全，建议采用 **方案 C（折中）**，只移除硬编码 API Key，保留用户自定义功能。
